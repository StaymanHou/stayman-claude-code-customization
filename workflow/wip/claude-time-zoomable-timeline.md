# Feature: Zoomable + draggable multi-track timeline (WP5)

**Workflow:** feature
**State:** plan (complete)
**Created:** 2026-05-22
**Entry:** spec → plan (complex feature — XL gated milestone)

## Problem Statement

The v1 `claude-time visualize` dashboard fits each rendered view to the available viewport width via a single `pct(start, end)` helper in `viz/dashboard.jsx` line 320, which maps minute-offsets within `DAY_RANGE_MIN` to CSS percentages. This works for day-view MVP but blocks every Phase 2 and Phase 3 v2 feature: Month view (30+ days), Custom-range, deep-zoom on short reading bursts, panning without re-running the CLI, and the shared interaction model that downstream WPs all consume.

WP5 introduces a `ViewportState = {visible_start_min, visible_end_min}` machine read by every segment renderer through a replacement `viewportPct(start, end, viewport)`. Pan and zoom are gesture-driven (drag on ruler/empty rows, wheel+cmd/ctrl, pinch, keyboard `+`/`-`/`0`/arrows/`Home`/`End`); a minimap re-orients after deep zoom. URL-hash carries viewport state for reload-survives. Performance budget (60fps at 1-month range with ~1800 segments) is measured at verify-self; canvas fallback is verify-self-driven, not plan-time-locked.

WP5 also codifies the **URL-hash state convention** in `CLAUDE.md` — the cross-cutting contract every downstream WP6–13 will follow when it adds state (filter chips, expanded projects, view tabs with params).

**Spec reference:** the `## Acceptance Criteria` section above this Work Tree (originally written at spec time, retained verbatim — 15 numbered criteria) is the verify-codify anchor. Plan-time decisions resolve the spec's 6 Open Questions inline (see "Plan-time decisions" section below).

## Acceptance Criteria

The feature is done when:

1. **Viewport state exists.** A `ViewportState = {visible_start_min, visible_end_min}` object lives in a `useViewport()` custom hook in `dashboard.jsx`, and all segment rendering reads from it. The legacy module-level `DAY_START_MIN` / `DAY_END_MIN` / `DAY_RANGE_MIN` constants are reduced to *initial-viewport defaults*; the segment-positioning path no longer references them directly.
2. **Pixel-from-viewport math.** A new `viewportPct(start, end, viewport)` replaces `pct(start, end)` and computes positions relative to the viewport. Off-viewport segments are **clipped** via CSS `overflow: hidden` on each row container (resolution: clip rather than cull; see Plan-time decisions).
3. **Pan works.** Dragging on the hour ruler or on an empty row updates `visible_start_min` and `visible_end_min` together, preserving zoom level. Cursor: `grab` / `grabbing`. The cursor stays anchored to the same data minute throughout the drag.
4. **Zoom works.** Mouse wheel + cmd/ctrl, two-finger trackpad pinch, keyboard `+` / `-` / `0` (reset). Zoom-anchored at cursor x-position. Zoom-in min: 1-minute viewport. Zoom-out max: full data window (clamped).
5. **Ruler tick density adapts.** Tick generator picks the densest interval producing 8–30 visible ticks. Scales: 1h → 30m → 15m → 10m → 5m → 1m.
6. **Minimap renders.** Single combined low-density track (~80px tall) at the bottom of the dashboard shows the full data window. Draggable "visible-window" rectangle pans/zooms via drag/edge-drag; click elsewhere re-centers viewport.
7. **Keyboard shortcuts.** Arrow-left/right pan by 10% of visible width. `+` / `-` zoom by 1.5x at viewport center. `0` resets to "fit data window." `Home` / `End` jump to data start / end (zoom preserved). Listeners attach at the Dashboard wrapper; don't fire when typing in any future text input.
8. **URL hash captures viewport state.** Hash shape: `#viewport=<start_min>:<end_min>` (integer-minute pair, decimal). On load, parse if present and apply. On change, `replaceState` (not pushState) debounced ~200ms.
9. **URL-hash state convention codified.** New `## Claude-time visualize URL-hash state` subsection in project `CLAUDE.md` documents: key shape (`key=value;key=value;...` separator `;`, URL-encoded values), merge semantics (each consumer owns keys via shared `updateHash(patch)` helper preserving others), reload behavior, default-elision rule, one-line examples per downstream WP slot.
10. **Performance budget — measured at verify-self.** With synthetic ~1800-segment 1-month dataset, pan and zoom measured at 60fps (or actual fps documented via `requestAnimationFrame` instrumentation). DOM-vs-canvas decision is verify-self-driven; canvas fallback is a verify-self-back-loop, not a plan deliverable.
11. **`requestAnimationFrame` throttling.** Every pan/zoom mutation goes through a single `rAF`-scheduled commit per frame.
12. **Playwright behavioral test.** New `tools/claude-time/test/test_visualize_interactive.sh` asserts at minimum: click+drag on ruler changes viewport, wheel+ctrl changes zoom, `+` key zooms in, URL hash updates after pan, reload with `#viewport=...` restores viewport. If Playwright MCP is unavailable at verify-self time, fall back to source-shape assertions only and SURFACE the gap.
13. **`test_visualize_cli.sh` source-shape assertions.** Source-shape assertions (independent of Playwright) confirm emitted HTML contains: `useViewport`, `visible_start_min`, `viewportPct`, ruler-tick-density adaptation, wheel/keyboard handlers, hash-read code, minimap render.
14. **No regression of Day view.** Default hash (no `#viewport=...`) produces visually equivalent v1 Day view; WP1's adaptive ruler still emits 17-tick output for 6:00–23:00. Strict superset on default path.
15. **Touch / mobile out of scope.** TODO comment marks the touch-event hookup point for hypothetical v3.

## Plan-time decisions (resolves spec Open Questions)

| Spec question | Decision | Rationale |
|---|---|---|
| Hash separator | `;` between pairs, `=` between key/value, values URL-encoded | `&` would mislead readers into expecting query-string semantics; `;` is visually distinct and well-precedented (matrix URIs, Lucene). |
| Minimap density | Single combined low-density track (~80px), all projects merged | Re-orientation is the only use case; per-project minimap is over-engineering for that. WP13 collapsed-row work can revisit if needed. |
| Event-handler attachment surface | Time-axis container only (`.timeline-area`) | Page-level wheel hijack would clobber browser scroll. Time-axis-only is the audio-editor convention. |
| Initial viewport for multi-day data | "Fit data window" (defaults to current data extent) | WP5 day-scoped exercise; WP7/8 will refine per-view-mode defaults. |
| Clip vs cull off-viewport segments | Clip (`overflow: hidden` on each row container) | Simplest; cull is a perf back-loop if measurement demands. |
| Viewport hook location | Source-side `useViewport()` custom hook in `dashboard.jsx`; wrapper-side glue plumbs URL-hash sync | Segment renderers in source need viewport access without prop-drilling. URL-hash sync glue lives in the `_interactive_dashboard()` wrapper alongside `view` / `selectedSegId`. |

## Test Triage — WP5-P1 codify "all 17 expected HH:00 ruler labels"
Classification: Obsolete test (newly written, never landed) — the assertion was written under a wrong mental model: it assumed the 17 hour-tick labels would appear as pre-rendered string literals in the emitted HTML. They don't — the labels are generated by a JSX template literal `${String(h).padStart(2,'0')}:00` that the browser's Babel-standalone executes at runtime against the result of `hoursInViewport()`. The source HTML only contains the template literal once and the runtime-computed hour numbers (`06..22`) never appear as `06:00`-style strings until JSX execution.
Confidence: high — the failure has exactly one explanation: assertion targets a post-Babel-runtime DOM state, not the pre-execution source HTML the CLI test inspects.
Evidence: `grep -oE '[0-9]{2}:00' /tmp/ct-debug2/d.html | sort -u` returns only `06:00`, `14:00`, `22:00` (none of which are runtime ruler labels — those are unrelated source-comment / data-payload occurrences).
