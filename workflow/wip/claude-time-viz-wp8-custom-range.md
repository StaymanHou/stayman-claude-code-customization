# Feature: claude-time visualize — Custom-range view (WP8)

## Problem Statement

The `claude-time visualize` dashboard currently has four toolbar tabs (Day, Week, Month, Custom). Day + Week are functional; Month + Custom are disabled stubs (4th arg `enabled=false` to `tabBtn`). This feature wires up **Custom**: a user-picked `[start, end]` date range that renders as the existing zoomable timeline over that arbitrary window. The CLI gets a peer `--range YYYY-MM-DD:YYYY-MM-DD` flag for parity. State persists in the URL hash so reloads + shareable links work, per the existing hash schema. This is mostly assembly work because (a) `build_range_data` already produces the right data shape (it's what WP5b's Day view multi-day window already consumes), (b) viewport + multi-day day-offset segment math already handles arbitrary `[0, dayCount*1440]` windows, (c) the URL-hash schema reserved `view=custom` + `range=YYYY-MM-DD:YYYY-MM-DD` slots ahead of time in `CLAUDE.md`, and (d) the `useFilter()` context from WP9 plumbs through `SegmentBar` so WP9's kind filters + project popover will Just Work in the custom view.

The remaining work is two genuinely new things: (1) the CLI flag + emit-time wiring, and (2) the UI surface (Custom tab + date-range picker) with hash round-trip and input validation. Plan-deviation lessons from WP9 baked into phasing: per-phase verify-codify (no centralized Phase 3 cleanup), surface-naming at plan time (date picker lives in the Toolbar's `dateLabel` slot — replaces the read-only label when `view === 'custom'`, matching the Day/Week pattern), and "downstream contract impacts" pass at phase boundaries (Phase 1's CLI/data-layer changes are consumed by Phase 2's renderer; Phase 2 lands all consumer edits at the same time).

## Plan-deviation lessons baked in (from WP9 retrospect)

1. **Per-phase verify-codify only** — no centralized "Phase 3 codify-cleanup". Each phase's codify pins land with the code it pins. (Lesson: WP9 plan had a Phase 5 codify phase that was redundant by exec time.)
2. **Surface-naming at plan time** — date-range picker is named at the actual surface (`Toolbar.dateLabel` slot, replacing the read-only label conditionally). Not "added to the toolbar somewhere". (Lesson: WP9 plan said "kind chips in Toolbar" but they ended up in the Legend strip — that was the right surface, but the plan should have named it.)
3. **Downstream contract impacts at the changing phase** — Phase 1 names the renderer consumer (`isCustom` branch, picker init from `today.meta_range`) so when Phase 2 lands, the contract handshake is already known. (Lesson: WP9 had to discover the consuming-surface placement during build twice.)
4. **Single-source-of-truth discipline** — `MAX_RANGE_DAYS` flows from Python config → `window.CT_MAX_RANGE_DAYS` → client-side validation. Don't hardcode 90 in two places.
