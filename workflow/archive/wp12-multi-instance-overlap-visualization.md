# Feature: WP12 — Multi-instance overlap visualization

**Workflow:** feature
**State:** plan (complete)
**Created:** 2026-06-06
**Entry:** spec (complex feature — WBS WP, final WP of v3 cycle)

## Problem Statement

When two Claude Code sessions ran in parallel on the same wall-clock minute (the user had two terminals open at once, or a long-running session ran concurrently with a fresh one), the existing claude-time visualize Day/Custom views render the two sessions as independent rows but give no visual signal that they overlapped. The dashboard implicitly invites the eye to read each row as a separate, sequential block of work; in reality, time was "double-counted" — minutes counted once toward Project A and once toward Project B. The reclassifier handles the **gap-overlap** math correctly (cross-session typing-debit reattribution against away gaps), but session-interval overlap during active bursts is undetected at render time and invisible in the visualization.

WP12 introduces a visualization-only layer that detects session-interval overlap client-side at render time and exposes it in three places: a marker on the collapsed-row track (per WP11 composition rule), a half-height vertical stagger on overlapping segments when rows are expanded, and a side-panel "Overlaps with" section + a 4th HeadlineCard tile ("X min parallel work") when overlaps exist in the visible viewport.

**Problem statement [Updated 2026-06-06: user-clarification at verify-human — collapsed-row marker scope change].** Original framing treated the collapsed-row marker as a unified "overlap exists in this row" signal regardless of which project the peer belongs to. User feedback at P2 verify-human refines this: the **collapsed-row marker** is specifically meant to flag **within-project concurrent sessions** (e.g., two terminals open in the same cwd, the same project alias). Cross-project overlaps remain meaningful at the **aggregate** level (HeadlineCard Parallel tile) and the **per-session inspection** level (SidePanel "Overlaps with" list + expanded-row overlay strip) — but the *collapsed-row marker* is the wrong place for them because every project gets at-least-1 marker from cross-project peers, drowning out the useful signal of intra-project concurrency. **Root cause unchanged**: the detector still correctly identifies all overlaps; the rendering layer for one specific surface (OverlapMarkerLayer) needs project-aware filtering. Scope unchanged at the data/detection layer.

## User Stories

- **As a user** reviewing my Day view, I want to see which segments of two sessions overlapped on the same wall-clock minute, so I can mentally separate "I was actually working twice as long" from "I worked these in parallel and the activity time is double-counted."
- **As a user** looking at the headline stats, I want a "parallel work" total alongside the existing active/subagent/away tiles, so I can quantify how much of my apparent activity was concurrent vs sequential.
- **As a user** with a collapsed project row, I want a subtle visual cue (not a full second row) that overlap exists in this project, so the collapsed view stays uncluttered while still revealing the existence of parallel work without forcing me to expand.
- **As a user** clicking a session in the side panel, I want to see which other sessions it overlapped with by id, so I can correlate against my memory of the day.

## Acceptance Criteria

The feature is done when:

1. **Detection (client-side, render-time):** A pure JS helper `_detectSessionOverlaps(projects)` returns a per-session overlap descriptor — `{sessionId: {overlapMs: int, peers: [{id, overlapStartMin, overlapEndMin}]}}` — given a list of `projects[].sessions[]` with `{start, end, id}` fields. Two sessions overlap when their `[start, end]` intervals intersect on the same day (cross-day overlap handled via the Custom-view `day_iso`-tagged aggregation: only sessions sharing a `day_iso` are candidates). The helper is project-agnostic — sessions from the same project alias can overlap (the user may have run two terminals in the same cwd).
2. **Expanded-row stagger:** When a project row is expanded (per WP11) and one of its sessions overlaps with another session anywhere in the viewport, the overlapping `[start, end]` portion renders at half-height with the upper half belonging to the row's session and the lower half belonging to the peer session. Non-overlapping portions render at full height. Each half carries a `data-overlap-peer="<peer_id>"` attribute.
3. **Collapsed-row marker:** When a project row is collapsed (per WP11), an overlap-indicator dot or hairline renders on the merged-by-kind band at every overlap interval contributed by any session in that project. The dot is visually subtle (no row-height change, no color change to the band itself), uses `data-overlap-marker` for selector-anchoring, and on hover surfaces a tooltip "Overlaps with `<peer_id>` for Nmin". The collapsed band's merge-by-kind union is unchanged; overlap rendering is purely additive.
4. **HeadlineCard 4th tile** (extending WP11's 4-tile layout to 5 tiles): "Parallel" tile shows total ms of parallel work across all overlapping session pairs in the visible viewport (per the active filterKinds gating — overlap minutes are only counted if both sessions' segments are visible-kind, e.g., active or subagent). When no overlap exists in the viewport, the tile renders "0m" rather than being hidden (consistent with WP11's away-tile-always-visible pattern). Selector: `[data-headline-tile="parallel"]`.
5. **Side panel "Overlaps with" section:** When a session is selected in the side panel and the detector returns peers for that session, a new "Overlaps with" section lists each peer by `id` (8-char), the overlap range (HH:MM–HH:MM), and the overlap duration. Section is omitted entirely when peers is empty. Selector: `[data-side-panel-overlaps]`.
6. **Filter gating:** The Parallel tile and the per-session overlap rendering respect `filterKinds` — overlap is only counted/rendered for segments whose `kind` is in the active filter set. (If user toggles off active+subagent, the parallel tile shows 0m even when sessions visually overlap, because the *visible* overlap is zero.)
7. **Custom-view cross-day support:** The same detector runs over `customPayload.projects[].sessions[]` (which carry `day_iso` tags), so cross-day Custom-range views surface overlap correctly even when overlap is on a non-default day.
8. **No URL hash key reserved.** Overlap detection is automatic; no user-tunable state. The 4th-tile presence is data-driven (overlap exists in viewport → tile shows nonzero; otherwise 0m).
9. **Mock-data smoke path:** `--demo` mode emits two overlapping sessions in the demo `viz/data.js` payload so a clean checkout (`claude-time visualize --demo`) shows the overlap visualization end-to-end without requiring real DB events. The existing demo data is extended (not replaced).
10. **Test pins:** CLI source-shape pins (selectors emit, detector reachable from build); container interactive behavioral pins on a seeded payload (synthetic 2-overlap fixture covering: expanded stagger renders both halves with correct peer IDs; collapsed marker count matches overlap count; HeadlineCard 4th tile shows correct ms; side-panel "Overlaps with" lists peers with correct ranges); pure-JS unit on the `_detectSessionOverlaps` helper covering edge cases (no overlap, partial overlap, full containment, three-way overlap, cross-day-in-Custom-view, empty input).

## Out of Scope

- **No reclassifier change.** The data layer remains untouched. Overlap is a *visualization* layer over the existing session shape.
- **No new session field on the payload.** Overlap is computed at render time from `session.{start, end}` — no `overlapMs` attribute attached to the session at build_window_data time. (The detector's output is a render-time-only structure, never persisted.)
- **No Week-view, Month-view, or Compare-view overlap rendering.** Those views aggregate at a coarser grain (full days/months) where session-interval overlap is not a unit of analysis. The same detector could trivially extend later, but is not in scope.
- **No overlap rendering at the **interrupt** level.** The session-internal `interrupts` array (interrupt UPSes) is unchanged; overlaps render at the session-interval level only.
- **No "overlap density" heatmap or visualization beyond marker + stagger + tile + panel section.** Future viz polish (e.g., a third sibling track for "overlap as separate lane") is explicitly not in scope per the resume-time decision.
- **No three-way overlap special-case rendering** beyond what falls out of the pairwise detector. If session A overlaps both B and C (and B overlaps C), the half-height stagger renders pairwise — the visual may stack/clip but no special "triple overlap" treatment is added. This is bounded by the user's actual usage pattern (two terminals is realistic; three concurrent Claude Code sessions is rare).
- **No live auto-refresh / re-detection on filter chip toggle latency.** Detection runs on every render with `useMemo` keyed on `(projects, filterKinds)`; standard React perf assumptions apply.

## Technical Constraints

- **Composition with WP11 collapsed-row rendering — pre-locked at resume:** marker-on-collapsed (the merge-by-kind union band is unchanged; overlap is a *separate visual layer* — a marker/hairline rendered at the overlap interval on top of the band). The collapsed band does not split or color-shift to indicate overlap; the marker is the entire signal.
- **Composition with WP10 viewport-aware row filtering:** when WP10's row-filtering hides a project from the viewport (no activity in visible hour range), that project's sessions are excluded from the overlap detector. Sessions filtered out by WP10 cannot contribute to the Parallel tile or the side-panel "Overlaps with" — the visible viewport is the unit of truth.
- **Reuses WP11 patterns:** the HeadlineCard 4th-tile slot (extending to 5 tiles), the `filterKinds`-aware computation (single source of truth via the existing `_computeAwayMsForWindow` pattern), the per-row data attribute discipline. **5th tile = "Parallel"** — extending the array literal that broke the `tileIds.length === 4` pin in WP11 (which is now `>= 3` and will accept 5). Plan-time grep at WP12 plan time: re-check `tileIds.length` assertions in tests.
- **No 3rd-party dependency.** Pure JS detection, no new libraries.
- **No CLI-side computation.** The detector lives in `viz_render.py::_interactive_dashboard` JSX (or factored into a sibling helper inside `viz/dashboard.jsx`) — runs in the browser at render time, not in the Python CLI.
- **Detector complexity:** O(N²) pairwise across N sessions in viewport is acceptable for the user's realistic session counts (≤50 per day). No interval-tree or sweep-line optimization needed for v3.
- **`session.id` is 8-char prefix already** (`underlying_sid[:8]` per `_build_viz_sessions` at viz_data.py:288). Collision probability across a 90-day window of realistic session counts is negligible; if collision is ever observed in the wild, surface as backlog and consider widening to 12 or 16 chars.

## Open Questions

- [x] **Q1: How does overlap viz compose with WP11 collapsed-row rendering?** **DECIDED at resume:** marker-on-collapsed (subtle dot/hairline at overlap intervals on the merged-by-kind band; band itself is unchanged; full half-height stagger only renders in expanded mode). Rationale: collapsed mode prioritizes density/scannability — a half-height stagger inside a single-line-per-project track would compress segments to one-quarter-height which becomes visually unreadable. The marker is the existence signal; expansion is the inspection affordance.
- [x] **Q2: Data shape — reclassifier metadata or client-side detection?** **DECIDED via investigation:** client-side detection. The reclassifier (`reclassify.py::cross_session_overlap_ms` at line 64) does cross-session reattribution against **gaps** only (Stop→UPS pairs for the typing-debit/away-bucketing math) — it does NOT detect session-interval overlap during active bursts. The session payload (`_build_viz_sessions` at viz_data.py:201) carries `{id, start, end, prompts, tools, segs, interrupts}` with no overlap metadata. Adding overlap metadata at build time would couple the data layer to a single-view concern (Day/Custom). Client-side detection over `[start, end]` interval intersection is simpler, contained to viz_render/dashboard.jsx, and scales naturally to filter-aware re-detection on every render.
- [x] **Q3: Validate via mock data.** **DECIDED:** extend `viz/data.js` demo payload with two overlapping sessions in the same day. A `claude-time visualize --demo` invocation will smoke-test the overlap rendering end-to-end on a clean checkout. Test pins lock the synthetic-data shape.

## Plan resolutions (set by feature-plan)

- **Spec correction — tile selector convention:** the spec line "Selector: `[data-headline-tile="parallel"]`" is overridden by the existing convention used by HeadlineCard at `viz/dashboard.jsx:1397`, which uses `data-metric-tile={t.id}`. Plan uses `[data-metric-tile="parallel"]` instead. The spec used "headline" descriptively; the source attribute is `data-metric-tile`. Test pins reference `[data-metric-tile="parallel"]`.
- **Expanded-row stagger — render strategy:** **overlay approach** (additive), not SegmentBar refactor. SessionRow continues rendering each `SegmentBar` at full height as today. Phase 1 adds a new sibling `<OverlapOverlayLayer>` component, rendered above the segs in `SessionRow`'s timeline column, that emits one absolutely-positioned `<div data-overlap-peer="<peer_id>">` element per overlap subrange. Each overlay covers the **bottom half** of the row at that subrange, with a translucent fill (CT_TOKENS-aware, peer-color hinted) — visually communicating "this time is shared with peer `<id>`". The full-height SegmentBar above remains untouched. This avoids forking SegmentBar's height/top math, keeps Phase 1's surface area small, and gives test pins a clean selector to count overlap regions. Filter-gating: the overlay layer reads `filterKinds` (same useFilter hook SessionRow uses) and skips overlay rendering for any overlap whose peer or own segs aren't currently visible.
- **Collapsed-row marker — render strategy:** in `CollapsedTrackRow`, after the merged-by-kind track renders, add a sibling `<OverlapMarkerLayer>` that emits one `<div data-overlap-marker>` per overlap interval contributed by **any session of this project** with **any peer session**. Each marker is a narrow vertical hairline (or small dot) positioned at the overlap midpoint, rendered at full row height with `pointer-events: auto` so `title=` tooltip works on hover. Visual: 2px-wide, peer-color-hinted, low opacity so it doesn't compete with the kind-band beneath it.
- **Detector home:** `_detectSessionOverlaps(projects, filterKinds)` lives at the top of `viz/dashboard.jsx` alongside `_computeProjectAwayMin` / `_computeAwayMsForWindow` (per CLAUDE.md "single source of truth" convention). Pure function (no React hooks). Returns the map shape declared in spec AC#1. Consumed by `_interactive_dashboard` via `useMemo` keyed on `(projects, filterKinds)`; result passed down via context or as props to `SessionRow`, `CollapsedTrackRow`, `SidePanel`, and `HeadlineCard`. **Implementation note:** to avoid prop-drilling through 4+ component layers, introduce a new `OverlapsContext` (React.createContext) populated at `_interactive_dashboard` and read via `useOverlaps()` hook in each consumer.
- **Cross-day handling in Custom-view:** sessions in `customPayload.projects[].sessions[]` carry a `day_iso` tag (per WP9's `_aggregateDayPayloads`). The detector's overlap predicate is `(a.day_iso || null) === (b.day_iso || null) && intervalsIntersect(a, b)` — only same-day sessions can overlap. For Day-view (no `day_iso` tags), the predicate's `(null) === (null)` collapses to "all-pairs" and overlap is detected within the day.
- **HeadlineCard tile sum (Parallel tile):** computed by `_computeOverlapMsForWindow(dayPayloadsByIso, startIso, endIso, filterKinds)` — mirrors `_computeAwayMsForWindow`'s shape. For each day in window, run `_detectSessionOverlaps` over that day's projects, sum the overlapMs across all sessions, divide by 2 (each overlap is counted once per pair-member). Filter-gating reads `filterKinds.active` and `filterKinds.subagent`: if both are false, return 0 (no visible overlap). For Custom-view, this same helper is called with `[range.start..range.end]`.
- **Phase split confirmed: 2 phases.** P1 covers detector + 3 render surfaces (expanded overlay, collapsed marker, OverlapsContext wiring) + selector emission. P2 covers HeadlineCard 5th tile + SidePanel "Overlaps with" section + demo-data extension + test pins. This split keeps P1's surface concentrated on the visualization core and P2's surface on the surrounding affordances + tests — mirrors WP11's clean P1/P2 split.

## Retrospect

- **What changed in our understanding:** The collapsed-row marker semantics are NOT a unified "overlap exists in this row" signal — they're specifically a **within-project concurrent-session** indicator (e.g., two terminals in the same cwd). Cross-project overlaps belong on the other surfaces (HeadlineCard tile, SidePanel list, expanded-row overlay) where the user can inspect the relationship in detail. The original spec + plan framed all four surfaces the same way (project-agnostic) — user feedback at P2 verify-human refined the scope. Lesson: when designing a "row-attached" UI signal in a visualization where rows have project-affinity, ask "what does this signal mean WITHIN a row's project vs ACROSS projects?" — these are often different signals with different intents, even when they share the same underlying data.

- **Assumptions that held:** (1) Client-side O(N²) pairwise detection is fast enough for realistic session counts; no perf concerns observed. (2) Reclassifier `cross_session_overlap_ms` (gap-overlap math) is orthogonal to session-interval overlap (active-burst-overlap) — confirmed at spec investigation; detector lives entirely in viz/dashboard.jsx with no data-layer coupling. (3) Demo data extension with distinct prefix IDs (s8/s9/s10) avoids the 8-char session_id collision hazard from `SURFACE-2026-05-22-VIZ-DATA-SESSION-ID-TRUNCATION-CAN-COLLIDE` — confirmed clean by verify-self. (4) The OverlapsContext pattern (single-source detector output distributed to all 4 consumers) avoided the prop-drilling cost a 4-surface render would otherwise incur.

- **Assumptions that were wrong:** (1) The OverlapsContext value being just `overlaps: {sid: desc}` was insufficient — P2.verify-human.2 F12 back-loop required adding `sessionToProject` to scope the marker. The decision to make OverlapMarkerLayer same-project-only meant the context needed richer data than the detector alone could provide. (2) The HeadlineCard empty-caption logic (`tiles.every(t.value_ms === 0)`) was assumed-correct from WP11 — turned out to be a latent bug masked at WP11 because the 4th tile happened to be 0 on demo data; WP12's 5th tile with 30m of overlap data exposed it. (3) Spec said `data-headline-tile="parallel"` as the tile selector — plan-time grep caught that the existing convention is `data-metric-tile={id}`. (Caught at plan, not build — exactly the kind of spec→plan refinement the plan-time "research before sealing" discipline is supposed to surface.) (4) My P2.8 plan-time downstream-contract grep was thorough for array-length and key-name but missed literal function-signature and literal variable-binding-name subcases — both surfaced post-hoc as 2 new `WP3-PLAN-DOWNSTREAM-CONTRACT-MISS` instances during the same WP. The convention needs the 4-subcase coverage that the CLAUDE.md bullet now spells out.

- **Approach delta:** Plan was 2 phases (P1 = core viz infrastructure, P2 = surfaces + demo + tests). Actual implementation followed that boundary cleanly, with one mid-flight refactor at P2.3 (Provider lift from inside DayTimeline up to `_interactive_dashboard` because SidePanel is a SIBLING of DayTimeline, not a descendant — caught when wiring the SidePanel consumer). One F12 verify-human back-loop refined the OverlapMarkerLayer scope (within-project only) and required extending the OverlapsContext value with a `sessionToProject` map + extending demo data with s10 (a within-project peer of s8). 2 verify-self in-place fixes (1 real code regression + 4 obsolete-test relaxations) per the established friction pattern. Net: 2-phase plan held; the F12 back-loop adapted scope per user feedback within the same phase — no plan revision (F23) needed.
