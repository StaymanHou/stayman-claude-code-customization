## Problem Statement

WP9 is the **last remaining Phase 2 WP** and the **bridging case** that closes the WP5–WP9 useMemo-with-v2-alias-fallback convention. The v3 Custom view currently reads `dayPayload` (the WP5 useMemo) which falls back to the v2 `today` alias key — meaning Custom view shows whatever single day the CLI pinned at `end_iso`, not the picked custom range. This is a latent bug from WP5: Custom view appears to "work" only because `dayPayload` always resolves to *some* day's data, not because it correctly renders the picked range. WP9 fixes Custom view by introducing a `customPayload` useMemo that aggregates `day_payloads_by_iso[d]` for `d ∈ [range.start..range.end]` (cross-day union, tagging sessions with `day_iso`) — a JS-side analog of the Python `build_range_data` aggregation. For ranges that fall outside the pre-rendered window, the RangePicker preserves the v2 reload-redirect-toast flow. **The same WP also strips the v2 alias keys** (`today`, `week`, `comparison`, `months`, `meta`) since (a) WP5/WP6/WP7/WP8 useMemo fallbacks become dead code the moment WP9's Custom-view routing lands, and (b) deferring cleanup to a separate WP10-cleanup-only WP creates a dangling task that the WBS doesn't account for. Two phases: Phase 1 = Custom routing + RangePicker + test pins; Phase 2 = v2 alias-key strip + useMemo fallback cleanup + test updates. Plan-time decisions A (route via `customPayload` useMemo per convention default; NOT fork `isDayLike`) and B (fold alias-key cleanup into WP9 as Phase 2) are recorded below in the Plan Decisions section.

## Plan Decisions (locked at plan time)

**Decision A — Custom-view routing: `customPayload` useMemo (option b), NOT `isDayLike` fork (option a).**
- **Rationale:** Convention default per CLAUDE.md "v3 sub-payload routing pattern" note. Forking `isDayLike → isDay + isCustom` would introduce a parallel render-path that Phase 3 (overlap viz, collapsible rows, row density — all read `isDayLike`) would have to maintain in two places. The useMemo keeps the render code un-forked.
- **Subtlety:** Custom view's data semantics ARE multi-day Day-like (matches `build_range_data`'s output shape). The useMemo MUST do cross-day aggregation in JS (union sessions per alias, tag with `day_iso`) — a naive single-day pick wouldn't be correct. The v2 alias `today` actually had this aggregation done server-side via a separate `--range` emit; in v3 there's no re-emit on range change, so the JS-side aggregation is the correctness mechanism.
- **Fallback semantics:** when `[range.start..range.end] ⊈ pre-rendered window`, `customPayload` returns the v2 `today` alias (which is `payload["day_payloads_by_iso"][end_iso]` on a `--window` emit — a single day, not the range). The fallback keeps Custom view rendering *something* while the RangePicker triggers the reload-redirect-toast for true out-of-window ranges.

**Decision B — Fold v2 alias-key removal into WP9 (as Phase 2), NOT a separate WP10-cleanup-only.**
- **Rationale:** Once WP9 Phase 1 ships, the four useMemo fallbacks (`dayPayload → today`, `weekPayload → week`, `comparePayload → window.CT_DATA.comparison`, `monthPayload → monthsMap[monthIso]`) become dead code. Deferring cleanup creates a dangling task the WBS doesn't account for. Bundling avoids a 1-task-WP10. Two-phase split inside WP9 isolates the cleanup verify-loop from the routing-change verify-loop.
- **Subtlety:** Phase 2 ALSO needs to migrate the `const { today, week } = window.CT_DATA;` destructure at `_interactive_dashboard:69` AND the static design-canvas Dashboard wrapper at `dashboard.jsx:3198` (which has the same destructure but is stripped at emit by `_strip_design_wrapper`). The `_initView` IIFE's emit-time-`custom` fallback reads `today.meta.{start,end}` — migrate to `window.CT_DATA.window.{start,end}` or `windowEndIso`-derived values.

**Decision C — `customPayload` shape: in-JS aggregation of `day_payloads_by_iso` per-day payloads.**
- **Per-day payload shape:** `{iso, label, hour_range, projects: [{id, alias, path, sessions: [{id, kind, segs, ...}]}], hour_range_by_day: {iso: [start_h, end_h]}, day_window: [start_h, end_h], meta: {start, end, day_count}}` (single-day case).
- **Aggregation logic for `customPayload`:** union the `projects[]` arrays from per-day payloads, keyed by `project.id` (alias). For each project, concat all `sessions[]` across days, tagging each session with `day_iso` (the source day). Merge `hour_range_by_day` (preserve per-day hour ranges); compute new `day_window` as the union of all per-day windows. Set `meta = {start: range.start, end: range.end, day_count: <range day count>}`. Set `label` to a human-readable range label (e.g., `"Mar 1 — Mar 7"`).
- **Empty handling:** if all per-day payloads in the range are empty, return `{empty: true, meta: {...}, projects: []}` — matches the existing `dayPayload.empty` consumer check at viz_render.py:684, 898, 927.
