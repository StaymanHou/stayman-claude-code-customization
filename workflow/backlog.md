## SURFACE-2026-06-06-DOCKER-INIT-RANDOMIZE-HOST-PORTS
- **Source:** Cross-project learning persisted from `replicator-1-0` WP13-operator-review-ui Phase 1 verify-self (2026-06-06). Full learning doc at `/Users/stayman/Personal/projects/replicator-1-0/.claude/learnings/2026-06-06-docker-init-randomize-host-ports.md` (scope: global).
- **Target level:** harness / global CLAUDE.md (`~/.claude/CLAUDE.md`) — proposed new "Docker / dev environment" section, OR addition to an existing dev-environment block.
- **Type:** harness behavior rule / safety pattern
- **Summary:** When initializing a new Docker Compose setup (or adding/changing a service that publishes a host port in an existing dev compose file), **randomize every host-side port from the ephemeral range (49152-65535) rather than using the service's well-known default.** The container-internal port stays canonical (postgres 5432, redis 6379, vite 5173, uvicorn 8000, etc.) — only the `host:container` left-hand side is randomized. Live incident in Replicator-1.0 (2026-06-06): frontend container mapped `5173:5173` collided with an unrelated host-side Vite project ("Web Flight Sim") already bound to 5173; the Replicator frontend container could not start, and Playwright verify-self for WP13 Phase 1 navigated to `http://localhost:5173/content-pool` and observed the wrong project's UI — reported BLOCKING fails for every UI outcome with the root cause being environmental, not code. Resolution: remap to `58329:5173` in `docker-compose.yml`. The same hazard exists for postgres 5432 (very common collision), redis 6379, and any other well-known default. Picking another default like 5174 is the wrong fix — it just delays the next collision. Randomize from the ephemeral range to make collisions vanishingly rare.
- **Proposed fix:** Add a global CLAUDE.md rule with four parts: (1) **At init time** (writing the initial `docker-compose.yml`, or scaffolding a service into one), pick a random host port for each `ports:` mapping via `python3 -c "import random; print(random.randint(49152, 65535))"`; before committing, run `lsof -nP -iTCP:<port> -sTCP:LISTEN` to confirm the port is free — re-roll if not. (2) **Add a one-line comment** next to each `ports:` entry stating the intent, so future readers don't "fix" it back to the default. (3) **`.env` indirection (optional, for multi-operator projects):** record randomized ports in `.env.example` under variables like `FRONTEND_PORT=58329`, then reference them in compose via `${FRONTEND_PORT:-58329}` — lets each operator override per-machine. (4) **Prod compose files** (`docker-compose.prod.yml`) can keep defaults — the reverse proxy / firewall layer in prod handles port assignment. The randomization rule is for **dev** compose only, where multiple project checkouts share one host. Also worth adding to `feature-verify-self/SKILL.md` (or the verify-self subagent prompt): when a subagent reports BLOCKING fails on every UI outcome but backend / API outcomes are PASS, **suspect environment-level misrouting** (wrong port, stale container, wrong host) before back-looping to build — inspect the served page title and entry script before classifying the FAILs as genuine. Full proposed wording in the learning doc.
- **Priority:** medium — applies broadly across project ecosystems (any project using Docker Compose with published host ports on a dev machine that hosts multiple project checkouts). Real incident this session (not a near-miss) — caused a complete verify-self misdirection that took non-trivial investigation to root-cause as environmental rather than code-level.
- **Status:** resolved (2026-06-06, commit 5872554) — closed by feature `docker-init-randomize-host-ports`. Scope landed: shortened guidance bullet (~5 lines) added to `skills/product-context/SKILL.md` Variant A. Scope deferred (per verify-human feedback): the verify-self detection clause was dropped — verify-self is observe-only; if the pattern recurs, the right home is a `debug-*` sidebar (e.g. `debug-environment-misrouting`).

## SURFACE-2026-05-29-LONG-CMD-TIMEOUT-AND-EXCLUSIVE-RESOURCE-CONCURRENCY ✅ RESOLVED 2026-06-07 (commit f0d86ed)
- **Source:** Cross-project learning persisted from `ops-data-hub` incident-email-ads-zero-in-daily-report codify step (2026-05-29). Full learning doc at `.claude/learnings/2026-05-29-pytest-timeout-and-concurrent-runs.md` (filename kept pytest-anchored to match origin; rule itself is ecosystem-general).
- **Target level:** harness / global CLAUDE.md (`~/.claude/CLAUDE.md`) — proposed new "Long-running commands" section or addition to "Using your tools".
- **Type:** harness behavior rule / safety pattern
- **Summary:** The default 2-min Bash timeout silently auto-backgrounds long commands (full test suites of any kind — pytest, jest/vitest, cargo test, go test, rspec, mix test, Playwright; full builds — `npm run build`, `cargo build --release`, webpack/Vite; big migrations, large codemods, bulk imports). The auto-backgrounded tool result can look like a failure and mislead Claude into re-invoking the same command, producing two concurrent processes. When both processes contend on a shared **exclusive resource** — shared dev/test DB, shared cache or artifact dir (`node_modules/.cache`, `target/`, `dist/`, `.next/`, Bazel/Turbo cache), port-bound process, lock file (Cargo/Bundler/git index), single-writer file/object — the second run races destructively on setup/teardown, cache invalidation, lock acquisition, or fixture lifecycle. Concrete near-miss this session: two `docker compose exec app pytest` runs almost raced on `Base.metadata.create_all` / `drop_all` against `ops_data_hub_test`; the second was user-backgrounded before reaching conftest setup. The pattern is ecosystem-independent — same shape fires for two `npm test` runs hitting a fixed port, two `cargo test` runs contending on `target/`, two migration tools locking the same schema-version row.
- **Proposed fix:** Add a global CLAUDE.md rule with three parts, all written ecosystem-generically (not pytest-specific): (1) **Estimate runtime + set `timeout` explicitly** for any full suite/build/bulk operation — list per-ecosystem ways to query test count (`pytest --collect-only`, `npx jest --listTests`, `cargo test -- --list`, etc.) or fall back to project CLAUDE.md prior-runtime data, then `timeout = expected * 1.5 + buffer`. (2) **Never start a second instance against a shared exclusive resource** — define "exclusive resource" explicitly (DB, cache/artifact dir, port-bound process, lock file, single-writer file/object); on auto-background, wait for the completion notification rather than re-invoking. (3) **When uncertain about runtime**, run a small subset first to gauge per-unit time before committing to the full suite (subset command varies by runner). Full proposed wording in the learning doc.
- **Priority:** medium — applies broadly across project ecosystems (any language with a shared test backing store, any build with a cache lock, any tool holding an exclusive resource). Near-miss this session, not a real incident, but the failure mode (schema race on concurrent migration, cache corruption, lock contention) is rare-but-destructive.
- **Status:** resolved (2026-06-07, commit f0d86ed) — closed by feature `long-cmd-timeout-and-exclusive-resource-concurrency`. Scope landed (Phase 1 + Phase 2): (a) new `## Long-running commands (GLOBAL)` section in `CLAUDE.snippet.md` codifying all three rules with ecosystem-general wording (pytest/npm/cargo/go/bundle examples as parentheticals, not canonical); (b) Rule 1 leads with "Consult the runtime registry; estimate only if absent; set `timeout` explicitly" + closing sentence on the update step; (c) new `### Runtime registry` subsection documenting the per-project `<proj-root>/runtimes.md` convention with canonical file shape + read/update discipline (read pattern, formula `ceil(observed_seconds * 1.5 + 60) * 1000` clamped to 600000, tracked-vs-untracked scope, per-project rationale); (d) project-root `runtimes.md` seeded for this repo with `./tests/check-structure.sh` (232s → use-timeout 408000) and `./tests/run-tests.sh` (3097s clamped to 600000 with explicit auto-background note); (e) 3 new structural pins in `tests/check-structure.sh` guarding section + subsection + runtimes.md frontmatter. Build-time meta-validation: Rule 1 + Rule 2 each exercised end-to-end during the build itself.

## SURFACE-2026-05-29-ALIAS-KEY-AUDIT-METHOD-MISSES-DESTRUCTURING
- **Source:** v3 WP3 Phase 2 verify-self (2026-05-29) — alias-key audit at build P2.4 used `grep CT_DATA\.` to enumerate what the v2 frontend reads off `window.CT_DATA`. Result: `week` alias key was not populated; Dashboard crashed on mount with `TypeError: Cannot read properties of undefined (reading 'projects')`. 3 BLOCKING fails at first browser-load attempt; fixed in-place during verify-self.
- **Target level:** documentation / convention
- **Type:** audit-method gap
- **Summary:** When auditing what a downstream consumer reads off a producer-shape object, `grep <obj>\.` only catches direct property access. - **Why it matters:** The whole point of the alias-key block in WP3 Phase 2 was to preserve the v2-frontend coexistence contract during the WP5–WP9 transition. An incomplete audit ships a broken dashboard.
- **Proposed fix:** Add a one-line convention to project CLAUDE.md under the existing "Claude-time visualize URL-hash state" section (or a new "consumer-shape audit" subsection): "When auditing downstream consumers of a shape, grep BOTH `<obj>\.` (direct access) AND `= <obj>` (destructuring/rebinding). Either pattern alone misses half the contract." Alternatively codify as a structure-check pin if cheap (probably not — too project-specific).
- **Priority:** medium — affects future WP9 verify-codify (where the alias keys get removed and the same audit logic applies in reverse) and any future cycle that bridges v2/v3-shape coexistence.

When pausing one feature to start another (or any cross-feature pause/resume), make a WIP commit on the paused feature's in-flight state first. Commits are cheap and reversible (`git reset --soft HEAD~1`, amend, or `git rebase -i` to clean up before the next ship)." - **Target level:** feature:spec (new `debug-*` sidebar skill — non-trivial design surface: trigger gate, instrumentation playbook, cleanup discipline)
- **Type:** new-work / new debug skill in the agent-pulled sidebar category
- **Summary:** Add a `debug-*` sidebar skill (working name: `debug-empirical-telemetry` or `debug-observe-runtime`) that forces a shift from static-analysis debugging ("read the code, reason about what it does, propose a fix") to empirical observation of the running system ("add logging/timing/counters, run, read the telemetry, then decide"). Real debugging frequently requires runtime evidence: insert prints/logs, add timing instrumentation, dump intermediate state, capture a stack at the failure point, run EXPLAIN on a query, sample a hot loop. Without an explicit prompt to switch modes, the agent loops on the static approach even after it has demonstrably failed. A sidebar skill in the `debug-*` family is the right shape: agent-pulled when stalled, runs to completion, returns to caller. Parallels `debug-bisect-known-good` (also a stall-recovery technique) but with a different mechanism (observation vs. bisection).
- **Suggested action:** Author `skills/debug-empirical-telemetry/SKILL.md` following the `debug-*` category convention (mandatory sections: `## Category Context`, `## When to use`, `## When NOT to use`, `## Procedure` with Gate Check, `## Pitfalls`, `## Termination` with `DEBUG-TELEMETRY-*` tokens + `RETURN-TO:` line). Gate suggestions: (a) ≥2–3 failed static-analysis fix attempts on the same bug, AND (b) the bug involves runtime values the agent cannot derive from code (timing, DB stats, env-dependent state, intermittency, perf). Procedure should walk: pick the smallest observable that would discriminate between current hypotheses → instrument (logging, timing, counter, EXPLAIN, etc.) → run → read telemetry → iterate or hand back a concrete cause. Include a cleanup-discipline step (remove or guard the instrumentation before exit) since stray prints in committed code is a real failure mode. Also: discoverability surfaces per the "new skill category needs three surfaces" lesson — caller-skill prose mentions in `feature-build`/`incident-investigate`/`task-act`, "Debug techniques" subsection rows in each relevant orchestrator AGENTS.md, note in `docs/product/transitions.md` sidebar section. Worth speccing rather than planning directly — the trigger gate and the instrumentation playbook both have non-obvious failure modes (over-instrumenting, leaving prints in code, instrumenting too late after the bug has been "guessed-fixed", picking the wrong observable).
- **Priority:** medium — real recurring agent-behavior gap that costs wall-clock time when it bites, but no active bug forcing it now; pick up after WP5 of claude-time-visualize-v2 or interleave when next debugging an empirical-shaped bug.

## SURFACE-2026-06-02-CODE-QUALITY-REVIEWER-SUBAGENT
- **Source:** Comparative analysis of `obra/superpowers` workflow system (2026-06-02). Full report archived at `docs/product/archive/research/2026-06-02-superpowers-comparison.md`. Code-quality reviewer reads the implementation against quality criteria (good patterns, appropriate abstractions, testability) — separate from "did it match the spec?" which is a different lens.

- **Summary:** This repo currently has no code-quality review pass distinct from spec-compliance verification. `feature-verify-human` mixes "did it do what the plan said?" ## SURFACE-2026-06-02-BEHAVIORAL-PRESSURE-TESTS-FOR-SKILL-LANGUAGE
- **Source:** Comparative analysis of `obra/superpowers` workflow system (2026-06-02). Full report archived at `docs/product/archive/research/2026-06-02-superpowers-comparison.md`. Specific borrow: superpowers' test suite includes **behavioral pressure tests** that plant rationalization-shaped inputs (e.g. "the test is flaky, just claim it passes", planted SQL injection bugs in review fixtures) and assert the skill resists. Distinct from this repo's transition tests (which verify "given input X, skill emits TRANSITION Y") and structural tests (`tests/check-structure.sh`).
- **Target level:** harness / tests (`tests/run-tests.sh` augmentation or new `tests/pressure/` group).
- **Type:** test-coverage expansion
- **Summary:** Current tests in this repo verify (a) transitions fire correctly given clean inputs, and (b) structural conventions hold (frontmatter, required sections, byte-pins). Neither tests whether discipline-bearing skill language **survives pressure** — i.e., whether `feature-verify-codify` resists a fixture that says "tests are flaky just merge it", or whether `feature-build` resists "this is a simple change just do it, no plan needed". Behavioral pressure tests are a meaningfully different signal: they test the *rationalization-resistance* of skill prose, which is the property that matters most when the model is mid-task and under time pressure. **User stance (per conversation):** maybe — existing tests are largely working, but there's potential value in more rigorous coverage. Not a priority pickup; defer until either (a) a skill failure mode in the wild traces back to language that didn't resist pressure, or (b) a future cycle has scope for test-infrastructure investment.
- **Why it matters:** This repo's principle is "advisory enforcement over hard blocks." That principle is unfalsified without pressure tests — every claim that "the prose is strong enough" rests on author intuition rather than measured behavior. If/when the principle gets challenged (a real failure mode where advisory framing let discipline lapse), pressure tests would be the empirical instrument to either defend the framing or surface specific prose weaknesses.
- **Suggested action:** Light spec when picked up. Sketch: add `tests/scenarios/pressure/` directory; each scenario is a YAML with a rationalization-shaped fixture + an expected-behavior assertion (must contain escalation language, must not emit transition-to-complete, etc.). Run on sonnet (haiku won't expose the failure mode reliably). Start with 3-5 high-value targets — verify-codify (Test Triage gate under "flaky test" pressure), feature-build (under "this is small just do it" pressure), incident-mitigate (under "ship the fix it's prod" pressure). Don't try to cover all 35 skills.
- **Priority:** low-medium — user-flagged as "maybe", not immediate; pickup signal is either a real wild failure tracing to weak prose, or a scoped test-infrastructure cycle.
