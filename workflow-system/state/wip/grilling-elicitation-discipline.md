## Problem Statement

Requirement elicitation is the thinnest part of this repo's front end. `feature-spec` §1 is three bullets ("Ask the user questions to clarify scope, user persona, and success criteria") with no serialization, no ordering, no stopping rule, and no guidance on *which* questions matter. `product-vision` §1 is a five-topic checklist (Core Problem / Proposed Solution / Target Audience / Success Metrics / Core Principles) — a form to fill, not a protocol. The repo's rigor is concentrated **downstream** (verify-self, verify-human, verify-codify, test-assertion-review, transition discipline); the front end assumes the operator arrives with a well-formed request.

The failure mode this leaves open is specific and invisible: **the operator cannot evaluate a spec's silences.** Reading a finished spec, they check what is on the page. They do not notice the decision that was never surfaced because the agent quietly picked a default. Serial questioning with a stated recommendation makes each default **visible and refusable one at a time** — which is exactly what a document review cannot do.

The technique that closes this is `grill-me` (Matt Pocock's `skills/productivity/grilling`, plus Vlad Gusinov's durable-capture fork). Its core is four moves: one question at a time ("asking multiple questions at once is bewildering"), walk the decision tree resolving dependencies in order, **the fact/decision split** ("if a *fact* can be found by exploring the environment, look it up rather than asking me — the *decisions*, though, are mine"), and a hard gate against acting before confirmed shared understanding. Each question carries a **recommended answer**, so the operator confirms or corrects in one word.

Stock grill-me is **relentless**, and that is correct for a standalone tool with nothing downstream. It is wrong here. This repo has three verification gates behind spec; relentlessness would spend the operator's attention — the actual scarce resource — re-confirming things that were already going to be caught. Two departures from the source are therefore load-bearing:

1. **A reversibility clause.** The fact/decision split covers *knowable vs. mine-to-decide*. It does **not** cover a third axis: decisions that are genuinely the operator's but **do not matter** (what to name a helper, whether a log line says "skipped" or "bypassed", which of two equivalent orderings). These pass the fact/decision test cleanly and stock grill-me would ask them. Adding "expensive to reverse" as a third conjunctive gate is what kills mundane questions.
2. **Budget-as-filter, not budget-as-cap.** A numeric cap ("max 6 questions") is arbitrary and will cut the wrong six. The filter is: *ask only where a wrong guess would go wrong silently and be costly to unwind.* Everything else becomes an explicitly-stated assumption. A well-understood feature may correctly grill **zero** questions.

Grilling is also **for the problem, not the solution** — a distinction the source cluster makes structurally, and which this spec adopts. Pocock's `to-spec` explicitly says *"Do NOT interview the user — just synthesize what you already know"*, then confirms one specific technical thing: the seams. Grilling proper aims at *what are we building, for whom, what does done mean, what is out of scope*. That is why `product-arch` is out of scope here (see Out of Scope) despite being a strong candidate on first inspection.

## User Stories

- As the operator running `/product-vision` on a fuzzy new initiative, I want the agent to put each consequential decision to me one at a time with its recommendation, so that I catch a wrong assumption at vision time instead of inheriting it through roadmap, arch, and WBS.
- As the operator running `/feature-spec`, I want the spec's non-obvious choices surfaced as questions and its obvious ones surfaced as a written **Assumed** list, so that I can refuse a default in one word rather than reverse-engineering it from a finished document.
- As the operator, I do **not** want to be asked about decisions that are cheap to reverse, so that grilling adds signal rather than friction.
- As the operator, I want to type `/util-grill-me` outside any workflow to stress-test a plan or decision before committing to it, so that the technique is available at the moment plans are actually made.
- As the operator running Mode 4 (FSD), I want grilling to be completely silent, so that unattended runs never block on a question.
- As a maintainer, I want the discipline's host pointers pinned by `check-structure.sh`, so that an undiscoverable skill cannot silently rot (the measured lesson from `arch.md` → `[Phase 20]`).

## Acceptance Criteria

The feature is done when:

**AC-1 — the standalone skill exists and carries the full discipline.**
`skills/util-grill-me/SKILL.md` exists as a `util-*`-category skill, with frontmatter `name` + `description` + `argument-hint`, a `## Category` section (util-family shape, **not** `debug-*`'s `## Category Context`), and it emits **no transition token** — neither F/I/T/P/S nor `DEBUG-*` — and carries **no** `RETURN-TO:` line, `skills:` key, or `tools:` key. The name follows the repo's `util-` prefix convention (`arch.md:360`) without exception.

**AC-2 — the three-clause gate is stated conjunctively and is the load-bearing rule.**
The skill states that a question is asked **only when all three hold**: (a) **not discoverable** from the environment (filesystem, tools, code, docs) — if it is, look it up instead of asking; (b) **the operator's to decide** — not the agent's; (c) **expensive to reverse** once built. Failing (c) → pick the sensible default, record it as an assumption, move on. The skill explicitly names clause (c) as this repo's **departure from stock grill-me** and states why (three downstream verification gates make relentlessness redundant).

**AC-3 — interview mechanics.**
The skill mandates: **one question at a time**, never batched; a **recommended answer** accompanying every question so the operator can confirm in one word; **dependency-ordered** traversal (settle the upstream decision before the ones depending on it); and a **hard gate** — do not proceed to writing the artifact until the operator confirms shared understanding.

**AC-4 — the Asked/Assumed output shape.**
Grilling terminates in a two-part disclosure: **Asked** (the questions put to the operator and their answers) and **Assumed** (every default taken without asking, each stated explicitly so document review still catches it). The skill states that the **Assumed** list is what preserves the existing single-pause review as a backstop, and that an empty **Asked** list is a valid, correct outcome for a well-understood request.

**AC-5 — drive-mode silence, by the existing rule and not a new one.**
The skill and both host blocks state that grilling is a **user-input prompt**, and therefore already forbidden on any AUTO transition by the existing **Hard rule for AUTO exits** (`skills/feature-spec/SKILL.md`, canonical table in `agents/feature-workflow/AGENTS.md`; P1 incidents 2026-05-16 / 2026-05-17). Consequence, stated explicitly: in **Mode 4 (FSD)** grilling **does not fire at all**. In Modes 1–3 grilling **reshapes the pause that already exists** at spec/vision entry — it does **not** introduce a new pause point. No new pause-policy row is added to any table.

**AC-6 — REVISED 2026-07-29 (F23 back-loop) — `product-vision` hand-off fork, not an inlined block.**

## Out of Scope

- **`task-plan`** — deliberately does not interview the user at all (`{{args}}` in, agent-side discovery, plan out). Tasks are atomic changes and bug fixes; its own scope assessment already **escalates (T3)** when a task turns out to need new models/API/arch decisions, and that escalation *is* the routing to a skill where grilling belongs. Adding an interview to the cheap fast path inverts the point of having a task tier, and the friction-to-value ratio is worst here: highest invocation frequency, smallest decisions. If a task genuinely needs grilling, the correct conclusion is that it is not a task.
- **`feature-plan`** — same reasoning, and additionally it is downstream of the spec where the problem is already settled. Its decisions are solution-shaped (which seam to cut), not problem-shaped.
- **`product-wbs`** — decomposition *does* surface genuinely new decisions (sequencing forks, seam choices, shared-dependency ownership); an earlier claim in this session that WBS operates only on already-settled inputs was **wrong**. It stays out on a narrower argument: the decisions decomposition surfaces are predominantly **structural** (sizing, dependency edges, ownership), and WBS already has two instruments for them — **Spike/Probe WPs** for real unknowns and **`design-priors.md` consult** for open product-design tradeoffs. This is a weaker "no" than the two above and is worth revisiting if priors-consult proves not to catch them.
- **`product-arch`** — the strongest *rejected* candidate, and rejected on a principle rather than on cost. Arch decisions are **solution/technical**, and grilling is a **problem-definition** instrument. The right technique for arch is the `to-spec` move — *synthesize the design, then confirm the **seams*** — optionally with `DESIGN-IT-TWICE` (parallel subagents under different design constraints, then "be opinionated — the user wants a strong read, not a menu"). That is a **separate follow-on feature**; folding it in here would produce a skill vague about what it is for. **Surface this to the backlog on finalize.**
- **Disk checkpointing** (Gusinov's incremental capture-after-every-answer). Rejected: with budget-as-filter most interviews are 2–4 questions, and a 3-question interview does not need crash protection. It would also force `product-vision` to create `vision.md` *before* elicitation (today §2 writes it after), changing that file's lifecycle and allowing a half-finished `state: in-progress` vision on disk. Revisit only if long interviews prove common.
- **The primitive/wrapper split** (a model-invocable `skills/grilling/` that hosts invoke by prose, per Pocock). Rejected for this repo: no skill here currently invokes another skill's prose — 48 self-contained SKILL.md files, no `references/` pattern — so it would set an architectural precedent `check-structure.sh` has no phase to understand; and `docs/lessons/harness-bootstrap-skip.md` bites harder, since editing the primitive would silently serve stale discipline to every host with no signal in the host file. Accepted cost of the chosen shape: **one drift surface** between the standalone skill and the two inlined blocks.
- **Retrofitting grilling into the `tutorial-*` tour arms.** Out of scope; the tours are heavily scripted narration.
- **Committing the reference clones.** Scratchpad only.
