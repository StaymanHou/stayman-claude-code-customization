## Problem Statement

The `claude-time visualize` subparser still carries the v2-era view-selecting flags (`--date`, `--week`, `--month`, `--range`, `--compare`, `--compare-range`, `--context-days-prior`, `--context-days-after`) and their entire `_cmd_visualize` handler branch (~333 lines at `claude-time:933-1266`) plus six dedicated helper functions (`_parse_month_flag`, `_parse_range_flag`, `_parse_compare_range_flag`, `_compare_window_bounds`, `_build_demo_comparison`, `_prev_month` — ~270 lines combined). WP3 added the unified `--window` flag and routes everything through it (v2 flags are silently no-op'd when `--window` is set or `--demo` is absent), but the legacy code path still exists and bare `--demo` still routes through it. WP4 deletes the legacy flags and their handler branch outright. Single-user tool, no external consumers (Decisions-locked #2 in wbs.md, 2026-05-26). The v3 branch must absorb the `--demo` path so demo still renders after deletion. User-facing toast strings in `viz_render.py` + `viz/dashboard.jsx` that reference removed flag names (`--date YYYY-MM-DD`, `--month YYYY-MM`, `--compare wow`) are rerouted to `--window` equivalents.

## Probe Findings (planning-time discovery)

The naive scope ("delete six argparse adds, delete handler branch, delete six tests") missed three load-bearing surfaces. Surfaced and incorporated as Phase deliverables:

1. **`--demo` survives but lives in the v2 branch.** The v3 branch at `claude-time:842` (`if args.window is not None or not args.demo`) explicitly bypasses bare `--demo` to the v2 demo path (`_load_demo_data`, `_build_demo_comparison`). After WP4 deletes that path, the v3 branch must own `--demo`. Phase 1 handles this (port `_load_demo_data` consumption into the v3 branch's window-emit flow).
2. **User-facing toast strings in `viz_render.py`/`viz/dashboard.jsx` reference removed flag names.** Three known sites: `viz_render.py:452` (`'--date', iso`), `viz_render.py:463/475` (`'--month', prevIso/nextIso`), `viz/dashboard.jsx:1075` (`claude-time visualize --compare wow` as empty-state-message). These render clickable toasts that auto-copy to clipboard — users would paste broken commands. Phase 2 reroutes them to `--window` equivalents (e.g., `--window YYYY-MM-DD:YYYY-MM-DD` for single-day, `--window YYYY-MM-01:YYYY-MM-LAST` for month).
3. **Test scope reduced — but not as much as the WBS suggested.** WP3 Phase 2 verify-codify deleted ~33 obsolete v2-flag scenarios but the WP11 Compare-view blocks (test_visualize_cli.sh:1531-1791) and Month-view click-day/arrow tests (interactive: js:126-748) still use `--month`, `--compare`, `--compare-range`, `--demo --compare wow`. Those test scenarios are NOT obsolete — they still pin source-shape contracts that Phase 2 (WP5-WP9) will eventually consume. They MUST be rerouted (not deleted) to `--window` invocations + `--demo` + URL-hash dispatch, so the pinned shapes are still exercised.

These three findings convert WP4 from "delete code" to "delete code + own one new responsibility (`--demo` in v3) + reroute a moderate set of user-facing strings and tests". Phasing chosen accordingly.

## Test Triage — comparison.{a,b}.metrics missing on real-DB emit (Phase 3 build P3.3, 2026-05-29)

**Classification:** Code regression — test is correct, new code broke it.
**Confidence:** High.
**Evidence:** v2's `_cmd_visualize` legacy branch (deleted in WP4 P1.3, line 1237-1238 of the deleted code) explicitly attached `_metrics_for_window()` results to `comparison.{a,b}.metrics` after `build_comparison_data` returned. WP4 P1.5 unwrapped the v3 branch and aliased `payload["comparison"] = payload["compare_payloads_by_preset"]["wow"]`, but `compare_payloads_by_preset` (built by `viz_data.build_window_data`) doesn't attach per-window metrics. Net: the legacy `.metrics` sub-key disappeared on real-DB emit. Downstream consumer is `CompareView` (`viz/dashboard.jsx:1081-1082`: `const aWall = aMetrics.engaged_session?.wallclock_ms || 0;`) — when `comparison.a.metrics` is missing, `aMetrics` is `undefined` and the view triggers the empty-state I just rewrote in P2.2. So this regression turns every real-DB Compare view into the "No comparison data" empty-state.
**Why this wasn't caught earlier:** Phase 1 verify-self exercised real-DB emit but only inspected source-shape pins; the Compare view's emit-time content rendering wasn't browser-tested end-to-end. WP3 Phase 2 verify-self (the alias-key audit) audited what frontend reads off `window.CT_DATA` but didn't grep for `.metrics` sub-key reads. CompareView's `aMetrics` destructuring is one level deeper than the alias-key grep targeted. This is exactly the "incomplete contract audit" pattern logged at `SURFACE-2026-05-29-ALIAS-KEY-AUDIT-METHOD-MISSES-DESTRUCTURING` (already in the backlog).
**Action:** Auto-fix code by attaching per-preset window metrics inside `build_window_data` — the right architectural layer (data layer owns shape; CLI layer doesn't need to know about compare-window metrics). Compute `build_metrics()` over A and B events for each preset and attach as `compare_payloads_by_preset[preset][side]["metrics"]`. After fix, re-run the suite. Audit-trail: the test_viz_data.py `BuildWindowDataTests` unit tests should ideally also assert this — but those live outside the WP4 scope; surface as a follow-up to backlog if not already covered.

## Retrospect

- **What changed in our understanding:** The plan-time probe correctly surfaced three load-bearing surfaces (`--demo` survival, user-facing toast strings, the breadth of WP11 Compare tests) but missed one structural contract — that `comparison.{a,b}.metrics` was attached at the **CLI layer** in v2's `_cmd_visualize`, not at the data-layer. The `build_window_data` shape contract didn't include that field, so deleting the CLI-layer attachment silently dropped the field on real-DB emit. This is a different shape of "downstream contract miss" than the v2 → v3 frontend coexistence concern we'd planned around — it's an *intra-component* contract that crossed CLI/data-layer boundaries.

- **Assumptions that held:**
  - `build_window_data`'s output was assumed to be the "right" shape — and after the metrics-attach fix, it is. The data-layer-owns-shape architectural call held up under contract restoration.
  - Phase splits (delete → toast/docs → tests) were correctly sequenced; Phase 3's reroute work was tractable because Phases 1+2 had stabilized the CLI surface.
  - Autopilot mode was the right drive choice — even with two mid-flight surprises, no human intervention was needed beyond the verify-human checklists and the user's explicit "run interactive tests in container" directive.

- **Assumptions that were wrong:**
  - Plan said `_load_demo_data` is "kept" and Phase 1 P1.6 would call it inside the v3 branch to "graft demo segments into the v3 payload's `day_payloads_by_iso[today]`." The actual implementation went further — synthesized the full v3 sub-payload skeleton (empty `month_payloads_by_iso`, empty `compare_payloads_by_preset`, empty `metrics`) plus the demo's `today`/`week` aliases — because the v3 frontend expects more than just `today` to be present. The plan understated the demo-skeleton scope.
  - The plan estimated 35 obsolete-test fails would be in scope for Phase 3 rerouting. After triage, the actual breakdown was 17 rewritten + 2 merged + 3 deleted + 8 interactive-test invocations rerouted. The plan didn't separate "reroute" from "delete" — Phase 3 turned out to need both.
  - "Test scope reduced — but not as much as the WBS suggested" — true, but the plan also missed that the same WP11-P1 block (lines 1531-1791 of `test_visualize_cli.sh`) needed a near-total rewrite, not a surgical reroute. The pinned shapes had drifted from the actual v3 emit shape even where the contract was nominally intact.

- **Approach delta:**
  - P3.1 (argparse-error pins) landed early in Phase 1 codify rather than waiting for Phase 3 sequencing. Structurally cleaner — the argparse pins ARE Phase 1's natural codification target (consuming-surface test for the contract change), and bundling them with the test_visualize_cli.sh edits at Phase 1 codify avoided a context switch.
  - Phase 3 P3.3 turned into a code-fix phase mid-build (data-layer metrics attach) rather than a pure tests-rewrite phase. Plan didn't anticipate this; the Test Triage gate at codify time caught it correctly and routed to auto-fix-code rather than test-update.
  - Phase 3 mid-build, user requested running the interactive suite in container ("tackle this now"). This caught 2 additional test gaps that source-only edits had missed (prev-month window precondition + URL-hash dispatch for Compare). Per the precedent established in Phase 1 verify-human, the user's direct steer mid-flow can productively expand scope when it surfaces real correctness gaps the planned verification path would have missed.

- **Surprises worth carrying forward (already filed to backlog):**
  - `SURFACE-2026-05-29-BULK-DELETE-MISSED-HELPER-IN-CLUSTER` — line-range deletes need a function-by-function enumeration check, not just a named-callers grep. Spatial proximity ≠ semantic membership.
  - `SURFACE-2026-05-29-WP3-PLAN-DOWNSTREAM-CONTRACT-MISS` (reinforced by WP4 P3.3) — the "plan-level downstream contract impacts" rule has now been missed three times. Worth codifying into `feature-plan` SKILL.md as an executable step.
